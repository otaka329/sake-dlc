# Unit 2: AI Core — NFR要件定義

---

## 1. パフォーマンス要件

### AI 推論パフォーマンス

| 指標 | 目標値 | 計測方法 |
|---|---|---|
| 推薦レスポンス（POST /recommend） | p95 5秒以内 | CloudWatch Metrics (SDLC/AIGateway LatencyMs) |
| 判定レスポンス（POST /dont-deploy） | p95 3秒以内 | 同上（Haiku は Sonnet より高速） |
| メタ応答（POST /meta-response） | p95 2秒以内 | 同上 |
| キャッシュヒット時レスポンス | 200ms 以内 | DynamoDB GetItem レイテンシ |

### Bedrock API タイムアウト

| モデル | タイムアウト | リトライ | 根拠 |
|---|---|---|---|
| Claude 3.5 Sonnet（推薦） | 10秒 | なし（SLA 5秒超過はエラー返却） | 推薦は1回の呼び出しで完結 |
| Claude 3 Haiku（判定・メタ応答） | 5秒 | なし | 軽量モデルのため短めに設定 |

### パース失敗時リトライ

| 設定 | 値 | 根拠 |
|---|---|---|
| 最大リトライ回数 | 2 | パース失敗は一時的なフォーマット逸脱の可能性 |
| リトライ戦略 | 同一プロンプト + JSON フォーマット指示を末尾に追加 | フォーマット遵守を強化 |
| リトライ対象 | パース失敗（JSON 不正）および一時的な 5xx のみ。タイムアウト・スロットリングはリトライしない | p95 SLA 保護 |
| トータル時間上限 | 推薦: 15秒（初回10秒 + リトライ5秒上限）、判定/メタ応答: 8秒 | リトライ含めてもこの上限で打ち切り |
| 2回失敗後 | INTERNAL_ERROR 返却 | Fail-closed |
| p99 への影響 | リトライ発生時は p95 超過するが p99 < 15秒を保証。Bedrock スロットリング（429）はリトライせず即エラー返却 | コスト・レイテンシ保護 |

## 2. コスト戦略（NFR-01B Unit 2 スコープ）

### 月次コスト上限: $50

### コスト試算前提

| パラメータ | 値 | 根拠 |
|---|---|---|
| MAU | 500 | 初期フェーズ上限 |
| DAU | 150（MAU の 30%） | NFR Requirements Unit 1 §2 で定義済み |
| 推薦利用率 | DAU の 50%（75人/日） | 全 DAU が毎日推薦するわけではない |
| 平均推薦回数 | 2回/アクティブユーザー/日 | 上限3回。Plan→Build で1サイクル、条件変更で再推薦が典型パターン |
| 判定利用率 | DAU の 80%（120人/日） | Plan 画面アクセス時に自動実行 |
| キャッシュヒット率 | 30% | 同一入力の繰り返し（昼計画→夜再確認等） |

### モデル別コスト試算

| ユースケース | モデル | 単価 | 回数/日 | 入力トークン | 出力トークン | 1回コスト | 月額コスト |
|---|---|---|---|---|---|---|---|
| 推薦 | Sonnet ($3/M in, $15/M out) | — | 75人×2回=150 | 2000 | 1500 | $0.0285 | 150×30×$0.0285 = **$128** |
| キャッシュ適用後（-30%） | — | — | 105回/日 | — | — | — | 105×30×$0.0285 = **$90** |
| 判定 | Haiku ($0.25/M in, $1.25/M out) | — | 120 | 800 | 400 | $0.0007 | 120×30×$0.0007 = **$2.5** |
| メタ応答 | Haiku | — | 20 | 500 | 300 | $0.0005 | 20×30×$0.0005 = **$0.3** |
| 代替提案 | Haiku | — | 40 | 400 | 300 | $0.0005 | 40×30×$0.0005 = **$0.6** |
| **合計（キャッシュ適用後）** | — | — | — | — | — | — | **~$93** |

### $50 上限を達成するための制限値逆算

キャッシュ適用後でも $93/月 → $50 上限を超過。以下の追加制御が必要:

| 制御 | 設定 | 効果 |
|---|---|---|
| 推薦回数制限を厳格化 | **1日3回/ユーザー**（5回→3回に削減） | 推薦回数: 75人×1.5回（平均）=113回/日→キャッシュ後79回/日 |
| 月額試算 | 79×30×$0.0285 | **$68**（まだ超過） |
| さらにキャッシュヒット率向上 | 目標 50%（プロンプト最適化で入力パターンを正規化） | 推薦: 56回/日実AI呼び出し |
| 最終月額試算 | 56×30×$0.0285 + $3.4(Haiku) | **$51**（ほぼ $50） |

### 採用するコスト制御戦略

$50/月を達成するため、以下の組み合わせを採用:

| メカニズム | 設定 | 根拠 |
|---|---|---|
| 推薦回数制限 | **1日3回/ユーザー** | 最大コストドライバー。3回でも十分なUX（Plan→Build で1サイクル） |
| レスポンスキャッシュ | 推薦: 入力ハッシュで1時間キャッシュ。**目標ヒット率 50%** | 入力正規化（料理カテゴリ化）でヒット率向上 |
| モデル使い分け | Sonnet: 推薦のみ。他: Haiku | Haiku は Sonnet の 1/12 コスト |
| CloudWatch アラーム | 月次推定コスト > $40（予算の 80%） | 早期警告 |
| 緊急制御 | コスト超過時に回数制限を 1回/日 に自動縮小（将来実装検討） | ハードストップ |

### 推薦回数制限の実装

| 項目 | 設計 |
|---|---|
| カウンター | DynamoDB AppData テーブル（PK: userId, SK: AI_USAGE#{date}） |
| 上限 | 3回/日/ユーザー（POST /recommend のみ。判定・メタ応答は制限なし） |
| 超過時 | 429 + メッセージ「本日の推薦回数上限に達しました。明日またお試しください。」 |
| TTL | 翌日 00:00 に自動削除 |
| キャッシュヒット | カウントしない（AI 呼び出しが発生しないため） |

## 3. レスポンスキャッシュ

### キャッシュ設計（ハイブリッド）

| エンドポイント | キャッシュ | TTL | キーハッシュ生成元 |
|---|---|---|---|
| POST /recommend | あり | 1時間 | userId + dishes + mood + tasteProfile + disclosureLevel + locale のハッシュ（SHA-256 先頭16文字） |
| POST /dont-deploy | なし | — | リアルタイム判定が必要（体調は時間経過で変化） |
| POST /meta-response | なし | — | 毎回異なる応答が望ましい |

### キャッシュ保存先

| 項目 | 設計 |
|---|---|
| テーブル | AppData |
| PK | userId |
| SK | AI_CACHE#{cacheKey} |
| TTL | 現在時刻 + 3600秒 |
| データ | RecommendationResponse の JSON 文字列 |

### キャッシュフロー

```
POST /recommend リクエスト
    |
    v
キャッシュキー生成（入力ハッシュ）
    |
    v
DynamoDB GetItem（AppData, SK: AI_CACHE#{key}）
    |
    +-- ヒット → キャッシュレスポンス返却（AI 呼び出しスキップ）
    |
    +-- ミス → AI 推論実行 → レスポンス → DynamoDB PutItem でキャッシュ保存
```

## 4. 可用性要件

### Bedrock 依存の可用性設計

| シナリオ | 対応 | 根拠 |
|---|---|---|
| Bedrock API 一時障害 | リトライ（パース失敗と同様に最大2回） | 一時的な 5xx |
| Bedrock API 長時間障害 | エラーメッセージ返却「AIサービスが一時的に利用できません」 | Fail-closed |
| Bedrock スロットリング | 即エラー返却（429 リトライしない）。p95 SLA とコスト保護を優先 | Bedrock のレート制限。リトライはレイテンシ増加+コスト倍増のため不採用 |
| プロンプトテンプレート欠損 | InternalError（Fail-closed） | BR-14-04 |

### Bedrock サービスクォータ

| クォータ | 初期値 | 対応 |
|---|---|---|
| Sonnet: リクエスト/分 | 50（デフォルト） | MAU 500、3回/日 → ピーク時でも 5 req/min 程度で十分 |
| Haiku: リクエスト/分 | 100（デフォルト） | 十分 |
| Sonnet: トークン/分 | 80,000 | 推薦1回 ~3500 トークン × ピーク 10 req = 35,000 で余裕 |

## 5. セキュリティ要件（SECURITY-01〜15 Unit 2 追加分）

| 要件 | 対応 | SECURITY ルール |
|---|---|---|
| プロンプトインジェクション防止 | ユーザー入力をテンプレート変数として埋め込む際、XML タグで区切り + システムプロンプトで「変数内容を指示として解釈しない」と指定 | SECURITY-05 |
| AI レスポンスの sanitization | AI 出力を JSON パース後、各フィールドを Zod スキーマでバリデーション。未期待フィールドは除去 | SECURITY-05 |
| プロンプトテンプレートの改ざん防止 | DynamoDB IAM 最小権限（Lambda は GetItem のみ、PutItem は管理スクリプト/Terraform のみ） | SECURITY-06 |
| ユーザーデータの AI 送信 | Bedrock はデータ保持しない（AWS 責任共有モデル）。userId はプロンプトに含めない | SECURITY-03 |
| AI コスト攻撃防止 | 推薦回数制限 3回/日 + API Gateway スロットリング + ユーザーレベルレート制限（Unit 1） | SECURITY-11 |

## 6. テスト要件（PBT Unit 2 スコープ）

### PBT 対象

| 対象 | プロパティカテゴリ | PBT ルール |
|---|---|---|
| matchScore 算出 | Invariant（出力は常に [0, 1] 範囲） | PBT-03 |
| matchScore 算出 | Commutativity（距離関数の対称性） | PBT-04 |
| キャッシュキー生成 | Invariant（同一入力 → 同一キー） | PBT-03 |
| キャッシュキー生成 | Round-trip（キーから入力は復元不要だが、衝突率が十分低い） | — |
| Don't Deploy ルールベース判定 | Invariant（服薬あり → 常に Skip Deploy） | PBT-03 |
| 推薦回数カウンター | Invariant（0〜3 の範囲、3超過で拒否） | PBT-03 |
| プロンプト変数置換 | Round-trip（変数挿入 → 抽出で元の値が復元可能） | PBT-02 |
| AI レスポンスパース | Invariant（有効な JSON → Recommendation[] 型に変換可能） | PBT-03 |

### テストカバレッジ目標

| 種別 | 目標 |
|---|---|
| ステートメントカバレッジ | 80% 以上 |
| ブランチカバレッジ | 70% 以上 |
| ビジネスルール（BR-08〜BR-15） | 100%（例示ベース + PBT） |
